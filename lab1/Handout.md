## Part 1: ROS2 in a nutshell

ROS (*Robot Operating System*) is not a traditional operating system: it is an open-source **middleware** that helps different processes (Python scripts, C++ programs, cameras, sensors, motors...) talk to each other. We use ROS2 and mainly its Python client library, **`rclpy`**.

### Workspaces, packages and nodes

- A **workspace** is a folder where we keep our packages and build outputs: `src/` (our source packages), and the autogenerated `build/`, `install/` (what we actually *source*) and `log/`.
- A **package** is the basic unit of organization: code plus metadata (source code, `launch/` and `config/` files, build files). We will meet two kinds:
  - **`ament_python`** packages hold Python nodes. Important files: `package.xml` (metadata and dependencies), `setup.py` and `setup.cfg` (how the code is installed and which *executables* it exposes), `resource/<pkg>` (a marker so that ROS2 finds the package) and an inner folder with the package's name, where the node code lives.
  - **`ament_cmake`** packages are used, among others, for **interface packages**: `package.xml`, `CMakeLists.txt` (declares the dependencies and interface files and generates the code) and the `msg/`, `srv/` folders.

```
luna_package/                    leds_rpi_pkg_interfaces/
├── package.xml                  ├── package.xml
├── setup.py                     ├── CMakeLists.txt
├── setup.cfg                    └── msg/
├── resource/luna_package            └── LedValue.msg
└── luna_package/
    ├── __init__.py
    └── luna_commander_node.py
```

- `colcon build` compiles everything under `src/` into `install/`, and **sourcing** (`source install/setup.bash`) makes the shell aware of our packages, launch files and executables.

> **Important:** Always re-source after every build!

- A **node** is a single running process. In Python we create one by subclassing `rclpy.node.Node`; it can have publishers, subscribers, service servers/clients, timers and parameters. To run it with `ros2 run <package> <executable>`, we add it to the `console_scripts` list of `setup.py`.

Useful commands: `ros2 pkg -h`, `ros2 run`, `ros2 node list`, `ros2 node info /<node_name>`.

### Interfaces and communication

Nodes talk to each other through **interfaces**, files written in the ROS2 Interface Definition Language that work between nodes written in different languages:

| Interface | File | Communication | Use it for |
|---|---|---|---|
| **Message** | `.msg` | one-way, continuous (*publish–subscribe* over a **topic**) | sensor data, commands, state |
| **Service** | `.srv` | two-way, on-demand (*request–response*) | quick requests, e.g. "what is your status?" |
| **Action** | `.action` | like a service, but for **long-running** tasks, with *feedback* and *cancel* | e.g. "go to this goal" |

It is good practice to reuse existing interfaces (e.g., `geometry_msgs`, `sensor_msgs`) for common robotic concepts. We can explore them from the terminal:

```bash
ros2 interface packages                        # all the interface packages available
ros2 interface show geometry_msgs/msg/Point    # structure of a message
ros2 interface show std_srvs/srv/SetBool       # structure of a service
```

A message is a list of typed fields (`int32`, `float64`, `string`, ...); in a service file the **request** is separated from the **response** with `---`. We can also write our own interfaces, as we will do in the LED exercise.

In Python, the basic building blocks are:

```python
self.pub = self.create_publisher(msg_type, topic, qos_profile)                 # topics: many publishers,
self.sub = self.create_subscription(msg_type, topic, callback, qos_profile)    # many subscribers
self.timer = self.create_timer(period_sec, callback)                           # periodic work
self.srv = self.create_service(srv_type, srv_name, callback)                   # services: one server, many clients
self.cli = self.create_client(srv_type, srv_name)
```

The *callback* is called automatically when a message (or request) arrives. We will use topics in both parts of this lab; services we will only meet through the CLI (see *Inspecting the ROS2 graph*).

### Parameters

**Parameters** are key–value pairs owned by a node. They let us change a node's behavior **without modifying its source code**.

- A node **declares** a parameter with a default value (`self.declare_parameter(name, value)`) and reads it with `self.get_parameter(name).value`.
- A parameter can be **static** (read once at startup, e.g., to create a publisher) or **dynamic** (read periodically, e.g., in a timer callback, so runtime changes take effect).
- Parameters are set from the code, from a **YAML file**/launch file, or from the **CLI**:

```bash
ros2 param list /<node_name>                       # parameters of a running node
ros2 param get /<node_name> <param>                # read a parameter
ros2 param set /<node_name> <param> <value>        # change a (dynamic) parameter
ros2 param dump /<node_name> --output-dir <dir>    # save them in <node_name>.yaml
ros2 param load /<node_name> <file>.yaml           # load them again
```

In a YAML file the top-level key is the node name and the parameters go under `ros__parameters`:

```yaml
/luna_commander:
  ros__parameters:
    linear_speed: 0.2
    period: 2.0
```

To *react* to a change (e.g., reject an invalid value or re-create a timer) a node registers a callback with `self.add_on_set_parameters_callback(callback)`, which receives the changed parameters (`name`, `type_`, `value`) and returns a `SetParametersResult` accepting or rejecting them. We will write one in the LED exercise.

### Launch files

A **launch file** is a Python script that **starts and configures multiple nodes** with a single command, with parameters, remappings and command-line arguments. It is kept in the `launch/` folder of the package and defines a `generate_launch_description()` function that returns a `LaunchDescription` with a list of actions. The main one is `Node(...)`:

- `package`, `executable`: what to run (the executable name from `setup.py`); `name`: the node's name
- `output='screen'`, `emulate_tty=True`: show the logs in the terminal
- `parameters=[...]`: a dictionary and/or YAML file with parameter values
- `remappings=[('old', 'new')]`: rename a topic/service without touching the code

`DeclareLaunchArgument` defines an argument with a default, and `LaunchConfiguration` reads its value (e.g., to pass it to a parameter). If a parameter is set in several places, the **launch file wins over the YAML file, which wins over the default in the code**. Launch files must be installed through the `data_files` of `setup.py` to be found, and are run with:

```bash
ros2 launch <package_name> <launch_file_name> <argument>:=<value>
```

### Wire up `setup.py` so `ros2 run` can find your nodes

If you try now to compile the project and run your nodes, it will fail to do so because we have not specified entrypoints for our scripts. For Python-based ROS2 packages, `setup.py` controls how your code is installed into the workspace and how executables are exposed. Key pieces:

- **`packages=find_packages(...)`** — includes your Python module(s)
- **`entry_points['console_scripts']`** — maps command names to `module:function` so `ros2 run <pkg> <name>` knows what to execute
- **`data_files`** — installs non-Python assets (like `launch/` and `config/`) into your package’s share directory so `ros2 launch` and parameter files are discoverable

After editing `setup.py`, rebuild and re‑source so the new executables/paths are visible.

### Inspecting the ROS2 graph

**How to peek inside ROS 2 graph activity:**

- `ros2 topic list` shows active topics; `echo` and `hz` help you inspect content and rate
- `ros2 node list` and `ros2 node info <name>` show nodes and their interfaces
- `ros2 param list|get|set` interacts with node parameters
- `ros2 service list|type|call` shows and uses the services

These tools are invaluable for debugging bringup and verifying that launch/parameters are doing what you expect.


```bash
# Topics
ros2 topic list
ros2 topic echo /pose
ros2 topic hz /pose

# Parameters
ros2 param list /luna_commander
ros2 param get /luna_commander period
ros2 param set /luna_commander period 0.1   # (will require re-creating the timer to take effect)
```

**Services:** we did not write any service in this lab, but ROS2 nodes offer some automatically! Every node serves its parameters through a set of *parameter services*. With Luna's nodes running, we can see them and even use them directly:

```bash
ros2 service list                                            # e.g. /luna_commander/get_parameters, /luna_commander/set_parameters ...
ros2 service type /luna_commander/get_parameters             # -> rcl_interfaces/srv/GetParameters
ros2 interface show rcl_interfaces/srv/GetParameters         # the request is on top of ---, the response below it
ros2 service call /luna_commander/get_parameters rcl_interfaces/srv/GetParameters "{names: ['linear_speed']}"
```

> The `ros2 param get` command from before does essentially this call for us! Can you find which service is behind `ros2 param set`?

You can also test the communication manually: publish a command to Luna yourself while only the driver is running, and watch the pose change:

```bash
ros2 topic pub -r 2 /cmd_vel geometry_msgs/msg/Twist "{linear: {x: 0.5, y: 0.0, z: 0.0}, angular: {x: 0.0, y: 0.0, z: 1.0}}"
```
